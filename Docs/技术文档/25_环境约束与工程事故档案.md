## 2. 4GB 显存：batch=1 是唯一干净档位

### 2.1 实测矩阵（D=125 + N=6144，单步 fwd+bwd，train_multimodal.py 第 64-72 行注释）

| batch | chunk | GPU 显存 | 单步时间 | 备注 |
|---|---|---|---|---|
| **1** | 512 | **2.55 GB** | **4.4 s** | 当前默认，唯一干净可用 |
| 2 | 512 | 4.78 GB | 49.4 s | **分配器碎裂，比 B=4 更慢** |
| 2 | 2048 | 4.95 GB | 38.9 s | — |
| 4 | 512 | 3.95 GB | — | 主进程提交 11.4GB / RAM 剩 0.27GB |

**关键读数**：B=2 chunk=512 比 B=2 chunk=2048 还慢（49.4s vs 38.9s）——显存不够时分配器行为非单调，**"调小 chunk 省显存"不一定更快**。

### 2.2 速度衰减实测（logs_sup.txt）

150 步短训实测速度从 **0.29 步/s 衰减到 0.17 步/s**（step 1→86，8 分 04 秒跑 86 步），同时：
```
[MEM:bench后] RAM 可用 1.33GB (load 91%) | 提交剩余 2.27GB/26.7GB
```
**速度衰减与 RAM load 91% 同步**——这不是 GPU 问题，是内存压力。任何"训练越跑越慢"的现象先查 RAM/提交量，不要先查模型。

## 3. C 盘 258MB 与 36.7GB 提交上限（隐形炸弹）

### 3.1 机理

16GB RAM + C 盘仅剩 258MB → pagefile 撑不开 → **系统提交上限被钉死在 36.7GB**。提交量（commit charge）顶穿时**不报错**，表现为静默挂死（GPU 0%）。

### 3.2 OpenBLAS/OpenMP 线程必须锁死（最隐蔽的坑）

**8 worker × 16 线程的 per-thread buffer 会顶穿提交量**，现象是**无报错静默挂死（GPU 0%）**。

纪律（写入交接文档硬件红线）：
> **OpenBLAS/OpenMP 线程必须在 import numpy/torch 之前锁死到 1**。

代码位置：train_multimodal.py 顶部（import numpy/torch 之前）：
```python
os.environ["OMP_NUM_THREADS"] = "1"
os.environ["OPENBLAS_NUM_THREADS"] = "1"
os.environ["MKL_NUM_THREADS"] = "1"
```
DataLoader 训练时 `workers=4`、`timeout=600`（防 worker 死了主进程永久阻塞）。

### 3.3 修复脚本（已写未执行）

`fix_pagefile_to_D.cmd`（v4200 目录）：把 pagefile 从 C: 移到 D:，预期"C 盘腾出 ~21GB 且解除 36.7GB 提交冻结"。需要**管理员权限 + 重启**。

**状态：未执行。项目铁律——清理 C 盘前先经用户批准。** 该脚本纯 ASCII（cmd 按 GBK 解析，中文路径会乱码）。

### 3.4 训练期监控判据（v4200 交接 TODO §P2）

盯两行日志：
- `[MEM:启动]` 和 `[MEM:bench后]`：**提交剩余要 > 2GB**，否则内存快顶穿；
- 显存占比别超 95%（早停判据四会盯着）。

## 4. 工程事故全档案

### 4.1 事故一：150 步试跑覆盖 3000 步 checkpoint（最严重）

**经过**：跑 150 步试跑时直接写 `outputs_real/overfit_ckpt.pt`，**覆盖掉已训好的 3000 步 checkpoint**。

**后果**：3000 步（约 3.5 小时 GPU）成果丢失，只能重跑。

**固化成的三道保险**（v3000 版本说明 §9A.2）：
| 保险 | 实现 | 作用 |
|---|---|---|
| ① 输出隔离 | `OVERFIT_TAG=<tag>` 环境变量，产物落 `outputs_real/<tag>/` | 试跑绝不污染正式产物 |
| ② 周期保存 | 每 250 步存 `overfit_ckpt_stepNNNN.pt` | 中途崩溃可断点续训 |
| ③ 最佳留档 | 对比度最接近 target 的那一步存 `overfit_ckpt_best.pt`，**永不被覆盖** | 训练后期退化也不丢最好的 |

**用法铁律**：
```bash
# 试跑/短验证 —— 必须带 tag
OVERFIT_TAG=_probe python scripts/overfit.py 150 8-ball_1f3b1.gif 3e-4 0 fixed log 20 0 4.0
```

**已知失效**：v3000J 训练启动于周期保存机制加入**之前**（`[SAVE]` 行在日志出现 0 次，`overfit_ckpt_best.pt` 不存在），中途无 stepNNNN 落盘。评估不重启（已跑 375 步占 12%、对比度正处上升期、剩余 3 小时崩溃概率低、已建立每小时看护）。

### 4.2 事故二：半成品编辑留下未定义变量（训练后必崩）

**经过**：03:00 有人把 `contrast_loss` 改成逐帧版，但：
1. 第 181 行引用了**从未定义的 `TGT_STD_PER_FRAME`** → 任何训练一跑就 `NameError`；
2. reshape 口径**是错的**：写成 `x.reshape(TS*WIN, GRID*GRID, pix)`，但实际 `N = TS*GRID*GRID`（`build_spacetime_index` 用 meshgrid(t,y,x)，grid=32=WIN），**N 里根本没有 WIN 维**——这么 reshape 等于把 5 个 win 帧混在一起算 std，退回全局口径。

**同类前科**：`update_baseline` 引用未定义变量 `step`（NameError 死在第 2 步）。已修：显式传 step。

**固化成的纪律**：
> **跑训练前先 `python -m py_compile` 一遍涉及改动的脚本**（项目历史上有人改一半留未定义变量的前科）。

### 4.3 事故三：早停判据误停（gap_ratio）

**经过**：早停判据二在 batch=1 时误停——train loss 是**单样本测量** vs val 是 **48 样本均值**，比值天然虚高，`gap_ratio=1.15` 触发早停。

**修法**：`gap_ratio` 从 1.15 提到 **3.0**。

**同类**：logs_final.txt 显示 `[WARN] 推算步数过少，检查 bench/rate`——7 天预算按 bench 速率（0.28 步/s）换算只推出 **40 步**（bench 速率与实际含数据加载的速率不符），且 `[DONE] 最佳验证 loss inf @ step 0`（best val loss 基线从未更新，inf 是初始值）。**7 天预算自适应步数机制本身未验证**（见 20 号文档 §4.5）。

### 4.4 事故四：loss 量级 650 万倍（一个 .mean(dim=0)）

**经过**：v3500 首轮 150 步验证出现方向完全相反的结果（网格比 1.663→2.281 越修越大、内部跳变 12.07→6.86 细节丢失）。

**根因**：`loss_noise` 拿到了带 batch 维的 `a_tar`（`[1,N,D]`），`(a_tar**2).mean(dim=0)` 在错误的维上求均值 → loss 量级 **1,553,134**，比主 loss（phase 0.24）大 **650 万倍**，梯度完全压倒一切。

**修复**：新增 `a_tar_n = a_tar[0]`（`[N,D]` 口径）专供新 loss 使用，**原有 loss 一行未改**（它们依赖广播对齐，改了会破坏 v2500 复现性）。

修复后量级平衡：noise 1,553,134 → **0.2324**。

**教训（写入纪律）**：
> 微调场景下，**新加的 loss 必须先单测量级**再启动长训练。一个手误的 `.mean(dim=0)` 就能让 150 步白跑，且现象极具迷惑性（看起来像「这个方向不对」，实际是数值 bug）。

### 4.5 事故五：preencode 路径退 3 级导致 14145 张静默跳过

**经过**：CLIP 预编码脚本路径计算退错 3 级目录，扫描不到 GIF 文件，但脚本不报错——**静默跳过**。日志 `logs_preencode.txt` 最终显示 14145/14145 全成功（1:24:08），说明修复后跑通过；但事故本身（静默失败模式）被记入档案。

**同类（静默失败模式总账）**：
| 静默失败 | 现象 | 防范 |
|---|---|---|
| 线程未锁死 | 无报错挂死，GPU 0% | import 前锁 OMP/OPENBLAS/MKL=1 |
| 路径退错 | 扫描 0 文件不报错 | 扫描后必须打印实际命中数 |
| 权重覆盖 | 旧 ckpt 被新试跑覆盖 | OVERFIT_TAG 隔离 |
| docstring 与代码矛盾 | `cond_field.py` docstring 第 156 行"逐通道归一" vs 代码 176-177 行逐位置中心化 | 以代码为准，顺手改 docstring |
| 判决脚本零输出 | 跑了但输出没存档 | 判决脚本必须落盘 + 登记进产物映射 |

### 4.6 事故六：GPU 调用必崩（device 缺失）

`codec/gif_codec.py` 第 302 行：`torch.zeros(...)` 缺 `device=z.device` → **任何 GPU 调用必崩**。CPU 上跑不出来（CPU 上 device 一致所以无症状），一上 GPU 就崩。v3000 修复。

### 4.7 事故七：min-max 出图绑架（显示层事故）

v2500 主出图 `normalize=True`（min-max）被离群 FFT 系数绑架：暗部被抬到灰，**灰度 std 24.5 vs target 53.2**。换固定 clamp 后 std 恢复到 34.7、PSNR 从 18.0 升到 20.0。后升级为主口径分位裁剪(0.5%,99.5%) + 副口径固定 clamp，**禁用 min-max 做质量评估**。

### 4.8 事故八：150 步短训被超时中断（v4200 最近一次）

**经过**：logs_sup.txt 计划 150 步，实际跑到 **step 86**（08:04）被中断，正是"条件未分化"争议数据（场差 5.7e-06、混合权重 std 0.00121）的来源——**这些数字是 86 步的读数，不是 150 步，更不是全量**。

**教训**：交接文档已明确标注"150 步（实际只跑到 86 步就被超时中断）"，但读数本身被引用时屡屡丢掉这个限定词。

## 6. 环境自检命令（给下一个 AI）

```bash
# 1. 确认解释器（必须 3.12.0 + torch 2.5.1+cu121）
C:\Python312\python.exe -c "import sys,torch;print(sys.version);print(torch.__version__, torch.cuda.is_available())"

# 2. 确认 GPU 空闲显存（训练前应 > 2.5GB）
nvidia-smi --query-gpu=memory.free --format=csv

# 3. 确认提交量余量（应 > 2GB，否则先解决内存再谈训练）
#    Windows: 任务管理器→性能→提交 已用/上限；或 PowerShell:
#    Get-Counter '\Memory\Commit Limit','\Memory\Committed Bytes'

# 4. 训练是否真在跑（日志停更 + 显存回落 = 已终止）
nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv -l 5

# 5. 跑训练前 py_compile
C:\Python312\python.exe -m py_compile scripts/train_multimodal.py
```
