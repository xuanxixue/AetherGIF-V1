| 半径 bin | 素材 | codec 顶 | 模型 | **模型/素材** |
|---|---|---|---|---|
| 0-4 | 1.0000 | 1.0000 | 1.0000 | 1.00x |
| 4-5 | 0.0106 | 0.0105 | 0.0142 | 1.34x |
| 8-9 | 0.0005 | 0.0005 | 0.0007 | 1.34x |
| 11-12 | 0.0001 | 0.0001 | 0.0001 | **1.84x** |
| 12-13 | 0.0000 | 0.0000 | 0.0001 | **2.21x** |
| 13-14 | 0.0000 | 0.0000 | 0.0001 | **2.88x** |
| 14-15 | 0.0000 | 0.0000 | 0.0000 | **4.23x** |

→ **越靠近 Nyquist 过冲倍数越大（1.0x → 4.23x）**，系统性而非随机。
素材和 codec 顶在这些频段完全重合 → **降采样本身无罪**
（实测 NEAREST/BILINEAR/BICUBIC/LANCZOS 四种插值 Sobel 均为 1042~1045）。
烧焦的真因是**模型在素材「从未被表示过」的高频区凭空生成了 2~4 倍能量**。

### 关键口径修正：之前那张表归一化到半径0，不是素材能量为 0
第一版径向约束用 `r >= 11`，算出 RING_TAR=0 → 误以为素材高频为 0。
**实际那 0.0000 是归一化后的显示值**，绝对能量非零：
素材 r>=11 占总能量 **99.99%**（因为 r>=11 包含了 r=11~90 的大半径区域）；
真正接近 Nyquist 的是最后 3 个等宽 bin（**r >= 72.4**，能量 1.37e12）。
→ 径向约束改成 `RAD_LO_FRAC = 0.80 × rmax`，口径正确。

### ★★ 踩到最隐蔽的坑：能量比口径完全不能用
第一版约束 1 用 `sum(a²)/sum(a_tar²)`，150 步实测增益恒为 **0.016**，约束永不激活。
但同一时刻日志的「频段振幅比」（mean_N 口径）读数是 **2.54（过冲）**。**两个指标差 150 倍。**
根因：中高段 `a_tar` 的 **std/mean = 2.1**（极度重尾），少数极大值主导 `sum(a²)`，
分母被撑大 → 任何模型输出都被误判成「欠幅」。
→ **约束口径必须与诊断读数口径一致**，否则约束和观测互相打架，永远学不会。
修正为 `mean_N(a_out) / mean_N(a_tar)`。

## 03:05 「结构性选择 + 学出来的选择能否共存」的调研
**结论：能，空间耦合本来就是 [1024,1024] 稠密矩阵，只是用解析式 Toeplitz 构造。**
```python
spatial_W = torch.exp(-self.lambda_s * s_scale * (diff ** 2).sum(-1))   # [1024,1024]
```
三条路（按推荐度）：
- **方案 B（最推荐）频率依赖衰减率**：`λ_s(f) = λ_base·(1 + β·log f_norm)`，**只加 1 个参数**，

## 12:30 Un-0（Unconventional AI）振子生图架构调研 —— 用户提问"他们怎么解决噪声问题"

用户在实现方案 B 前提问：Un-0 那种振子相位计算模型当初肯定也遇到"脏/噪声多"，

### ★ 核心结论：他们的病和我们的病根因不同，但解法可迁移
Un-0 的病不是"高频烧焦"，是**稠密耦合导致的同步坍缩**。但他们的诊断**精确命中 v3700 现状**：
> Dense models easily fall into catastrophic synchronization into a globally locked,
> zero-gradient state. Sparsity breaks this all-to-all coupling, allowing the network to
> maintain high-dimensional dynamics via chimera-like states and preserving the
> dimensionality of the dynamics even as the system scales up.

| Un-0 病症 | v3700 读数（命中） |
|---|---|
| 全局锁定、零梯度 | wcos=+0.9983（几乎完全锁相） |
| 维度坍缩、动力学压平 | target 逐通道跨 238x，模型只有 102x |
| 分布塌到少数模式 | profile_cos 0.997 但 ratio_logstd 0.30（谱被压平） |

### Un-0 两条解法
1. **稀疏化耦合矩阵**（主解法，FID +1.9）
   - 随机稀疏：训练前随机删 s 比例连接，留 (1-s)·N²
   - 模块化稀疏：振子分 Z 组，组内全连、组间不连，留 N²/Z
   - ImageNet64 上 Z=16 砍 93.75% 连接，FID +1.9；随机 75% 亦提升
   - **最优 LR 随稀疏度放开：η ∼ (1-s)^(-1/3)** —— 稀疏性能吃更大 lr
   - 超过临界稀疏度反而有害（通信断裂）；稀疏是控制旋钮不是单调正则
   - 模块会**按功能**特化：m7 控背景色、m1 控朝向、m3/m6 控车身色
2. **Drifting Loss（感知 + 分布匹配，不是逐样本重建）**：把生成图喂冻结
   DINOv2，在**特征空间**算 loss。核实原文（Deng et al. 2026, arXiv:2602.04770）
   后的精确机制：先估漂移场 V（核加权 mean-shift，把生成分布推向数据分布），
   再 `target=(gen+V).detach(); mse(gen,target)`。两个关键性质：
   ① 匹配的是**分布统计**不是逐系数，② 高频噪声在 DINOv2 特征里不存在
   → 模型没动机生成噪点。这是对"不该学的也学了"的对症药。
   代价：解码器只承担 12% 参数；且只在终点 T=1 施加损失，不监督整条轨迹。

### 对方案 B 的启示
方案 B（频率依赖衰减 λ_s(f)）与 Un-0 模块化稀疏**同源**——都是"不该耦合的别耦合"。
但 Un-0 证据指向：**按功能分组的模块化稀疏 > 按频率切**（更贴近内容选择）。
不改变当前计划：B 参数最少可严格对照，先跑 B 验证"耦合层是否需要频率选择性"，
这是 A/C 的前提。若 B 有效，下一步直接考虑模块化稀疏而非纯频率衰减。

### 其他细节
- Un-0 只有相位 θ（无独立振幅 a），读出用 sin/cos pair；我们是 (a,θ) 双场
- Un-0 训练用**显式 Euler**（不是 rk4），消融覆盖 1/2/5/10 步，训练后模型用
  10 步；评测换 dopri5 自适应/更多步时 FID 只升约 3%（未过拟合到积分器）

  noise 只作为"随机初始相位=扩散噪声"的类比。所以不能说"Un-0 解决了高频烧焦"——
  它是从架构上**没有这个通道/没有这个 loss**，不是治好的

2. `learn_g = g_core + sigmoid(edge_soften)·g_edge` 乘进振幅 loss

- 结论：**jina-clip-v2 的 model.safetensors 本身就含 text_model.transformer.*（488 键）**，
  独立下载的 jina-embeddings-v3 权重（1.14GB）其实用不上

### CLIP 实测定量（写死不能改的数）
- 参数量 865M（视觉 304M / 文本 561M），输出 1024 维
- 视觉塔**原生 512×512**（patch 14）。写 224 会 assert 崩：
  "Input image size (224*224) doesn't match model (512*512)"。有绝对位置嵌入，不能插值降分辨率
- 归一化常数必须用 CLIP 的 (0.4815,0.4578,0.4082)/(0.2686,0.2613,0.2758)，**不能用 ImageNet 的**
- 文本语义对齐实测：同义 0.80~0.83 > 异义 0.39~0.57，中英跨语言成立
- fp32 前向在 4GB 卡上 OOM → 预编码默认 CPU
- 内存 15.7GB / 可用 7.1GB，bs=1..4 稳定在 RSS 4.7~4.8GB

### ★ CLIP 各向异性（死穴级，14145 真实 GIF 实测）
原始两两余弦：均值 **0.853** / std 0.077 / 范围[0.666, 0.975]
去均值后：      均值 **-0.063** / std **0.343** / 范围[-0.705, 0.689]
→ **std 提升 4.5 倍**。不做去均值，所有 GIF 条件向量几乎一样，
CondProjector 之后的 4 个调制头学不到素材差异，表现为「loss 正常但生成千篇一律」。
已做进 `ClipConditionEncoder.center_normalize()`，preencode 落盘前统一应用，
并把相似度统计写进 meta.json（text_sim/image_sim）便于复查。

### ★★★ 4GB 卡的正解：CLIP 塔级分裂（2026-10-14 02:00 突破）
jina-clip-v2 两个塔行为差异极大，**必须分开安置**，这是小显存跑 CLIP 的通用解法：

| 塔 | 体积 | 行为 | 归属 |
|---|---|---|---|
| 视觉塔 | 304M | 512×512 前向，fp16 占 1.73GB | **GPU fp16** |
| 文本塔 | 561M | word_embeddings 250002×1024，LoRA 分支每次对**整个词表**做 matmul | **CPU fp32** |

- CPU 上视觉塔单张 **20~30 秒** → 14145 张 = **100+ 小时**，完全不可行
- GPU fp16 视觉塔 **3~4.8 张/s** → 全量 **49~80 分钟**，快两个数量级
- **LoRA 的 490MB 分配与 batch_size 无关**：bs=1/8/64 报错数字一模一样
  （"Tried to allocate 490.00 MiB"）。别试图靠调小 batch 解决
- 加载顺序：**CPU 加载 → 视觉塔 .half().to(cuda) → 文本塔留 CPU**。
  先 `.to("cuda")` 再 `.half()` 会在加载阶段就 OOM（fp32 权重 3.5GB）
- 塔级分裂后图像峰值从 2.58GB 降到 **1.07GB**
- `get_text_features` 的输入张量必须放 **CPU**（跟文本塔同设备），用 `_text_on_cpu` 标志
- `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 缓解碎片

### 静默失败教训（本次踩了 3 次同类坑）
- **别在 preencode 运行时同时跑 CLIP 基准测试**：两个 3.5GB 实例抢内存 → 两次 exit 139
- **psutil 判断进程死活会误报**：连续两次读到"CPU 增量 0.0s"，实则 5 秒消耗 9.42s（多线程）。
  psutil 的 cpu_times 有缓存，要重新取对象。判断卡死要看 **IO read_bytes 是否增长**
- **日志重定向要加 `-u`**：Python 缓冲会让日志长时间空白，看起来像卡死
- `np.save` 会**自动追加 .npy 后缀**：传 "x.npy.tmp" 实际写成 "x.npy.tmp.npy"，
  导致 `os.replace` 找不到文件。临时名要用 `xxx_tmp.npy`

## 2026-10-14 02:30 早停 + LR 调度（"上限 7 天，越快越好"）

用户澄清：不是"跑满 7 天"，而是**最早什么时候验证集达标就停**。7 天是上限，下限可能 2~3 天。

### ★★★ 早停不能按样本划分验证集（本次最关键发现）
实测：按样本随机划 424 条验证集，其 **80 个 group 全部**出现在训练集里。
原因：`bulk_mid_16_40` 等 group 各有上万 GIF，同 group 的 GIF 画面高度相似
（同一角色/同一素材库）→ 等于训练时见过验证样本的"近亲"，验证指标偏乐观，
早停会偏晚触发。
**必须按 group 整组划分**：8% group = 16 组 / 251 条，group 重叠 0，固定种子 1234。
（3% 只有 105 条，方差偏大；8% 只扣 1.7% 训练数据）

### 其他纪律
- 训练与验证**共用 compute_loss()**。验证侧另写一份 = 在比两个不同口径的数字，分叉判据全失效
- 验证集固定 `mode="both"`（确定性，不掷随机数），指标可复现
- 判据二要用 **train loss 的 EMA** 而非单 batch 值（单 batch 抖动大，会假性"分叉"）
- 早停时同时存 `best.pt`（后段可能已过拟合，末步权重不一定最好）
- **早停器 + 调度器状态必须进 ckpt**，否则续训后 `no_improve` 清零、lr 回 warmup 起点，
  会白等一整轮。已存 stopper{best_val,no_improve,band_hist,baseline_step_time} + sched{cur}

### 四条判据的实现要点
| 判据 | 实现 | 单测 |
|---|---|---|
| 一 连续不改善 | `best_val - val > min_delta` 记改善，否则 `no_improve++`，≥patience 停 | ✓ |
| 二 loss 分叉 | `val/train_ema > 1.15` 连续 3 次 | ✓ |
| 三 频段比稳定 | 连续 4 次落在 [0.8,1.2] 且 `max-min ≤ 0.01` | ✓ |
| 四 效率崩溃 | 单步时间 > 基线×1.8 连续 3 次，或显存 > 97% | ✓ |

- `min_steps=300` 保护：早期噪声大，防止第一次检查就误停
- 判据四的基线单步时间用前 300 步滑动平均（避开首步编译/预热抖动）
- `--no-early-stop` 可关掉做对照实验

### LR 调度（WarmupCosineLR）
`3e-5 --warmup 300步--> 3e-4 --cosine--> 1e-5`，总步数由预算算出后回填。
单测：warmup 后单调不增 ✓ / 峰值不超 lr_peak ✓ / 终点 = lr_min ✓
> 早停 + LR 调度的联动：退火后期验证指标更早进入平台期 → 早停更早触发 → 总时长更短
